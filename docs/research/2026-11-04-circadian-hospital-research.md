## Architecture options awaiting selection

A. Recommended: TypeScript, React/Next.js with pre-rendered public content, Node.js endpoints and PostgreSQL. Hostinger VPS runs the production application behind Nginx with TLS, compression, caching, process supervision and backups. Sites uses its supported Vinext/Worker workflow for a separate review deployment; platform-specific configuration must be maintained and tested separately. A Sites URL is not a Hostinger deployment.

B. Alternative: WordPress/PHP and MySQL on Hostinger. Easier familiar content editing, with added plugin/security maintenance and more constraints around a custom polished frontend. A separate Sites presentation would not automatically sync WordPress content.

5,000 visits/day is about 0.058 visits/second averaged across the day, not a peak capacity specification. Final sizing depends on pageviews, peak concurrency, request cost, actual VPS resources and load testing. Cache public pages; do not query PostgreSQL for each page render unnecessarily.

If an enquiry form is approved, collect minimal contact details and an optional appointment preference with consent. Do not request medical records through an ordinary marketing form. Server validation, abuse controls, idempotency, reliable persistence and an honest request-received state are required. A request is not a confirmed appointment. Admin access needs authentication and least privilege; database access stays private. No fake form success or placeholder delivery mechanism.

## Follow-up: Python and frontend comparison

Owner requested deeper language research before selection. This supersedes treating the original all-TypeScript recommendation as a settled choice.

Python is a suitable backend language for this project. Browser presentation still uses HTML/CSS/JavaScript, with TypeScript as a development language that compiles to JavaScript. The backend language does not determine visual polish or SEO ranking.

Official sources inspected:

- https://docs.djangoproject.com/en/5.2/intro/overview/ — database models, templates, forms and the integrated application framework.
- https://docs.djangoproject.com/en/5.2/ref/contrib/admin/ — built-in model-oriented internal administration; not a public frontend or complete editorial CMS by itself.
- https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/ — production configuration, HTTPS, secrets and deployment checks. A framework alone does not make a deployment secure.
- https://fastapi.tiangolo.com/features/ — API-focused capabilities, validation, authentication primitives and automatic API documentation. A publishing/admin experience still requires separate design and implementation.
- https://nextjs.org/docs/app/api-reference/functions/generate-metadata — server-rendered metadata.
- https://nextjs.org/learn/react-foundations/server-and-client-components — server/client boundaries and selective interactive components.
- https://nextjs.org/docs/app/guides/self-hosting — self-hosted Node deployment considerations.
- https://docs.astro.build/en/concepts/why-astro/ — content-driven architecture and selective client-side JavaScript.
- https://www.hostinger.com/support/the-most-frequently-asked-questions-about-hostinger/ — current Hostinger confirmation of Django on VPS. No OS reinstall or one-click image replacement should be performed on an existing server as part of routine deployment.

Frontend assessment:

| Option | Fit here | Tradeoff |
| --- | --- | --- |
| Next.js/React + TypeScript | Strong if appointment flows and patient-facing interactions will grow; supports static/server rendering and route metadata | Easy to ship too much JavaScript unless client components stay small; Node runtime adds operations |
| Astro + TypeScript | Particularly strong for a mostly informational hospital/SEO site; static pages with small interactive islands | Publishing from Django needs a rebuild pipeline or server adapter; complex application flows need more integration |
| Django templates + small JavaScript modules | Strong low-complexity deployment, server HTML and integrated admin | Rich React-style application flows require additional frontend work; capable of polished design nonetheless |

Backend assessment: Django is the preferred Python option for this site's potential content and enquiry management because it includes ORM, forms, authentication and internal admin. FastAPI is reasonable for API-centric services but offers no clear advantage for this scope that offsets assembling those management features. Neither needs microservices for the stated traffic.

Revised recommendation after comparing the current scope: Astro/TypeScript public frontend + Django/Python backend + PostgreSQL on Hostinger VPS. The explicit brief prioritizes organic search, content, photography and contact conversion rather than a patient portal. Build public pages as static HTML with small interactive islands and route admin/enquiries to Django. Content publication needs a reliable rebuild-and-deploy hook with visible failure handling. Next.js/TypeScript is the leading alternative if a substantial patient portal or complex real-time appointment interface becomes a confirmed requirement. This is a product-fit judgment, not a universal speed ranking.

Separate frontend/backend projects mean more build and upgrade work than a Django monolith. A static Astro export avoids a permanent frontend Node process; Node is needed for builds. A server-rendered Next.js alternative normally adds a Node process alongside Django. Do not add Redis, Celery, Kubernetes or a separate FastAPI service without a demonstrated need. Any eventual versions must be pinned to supported patch releases at implementation time.

Sites deployment constraint: its documented server runtime is JavaScript/Workers, so a Django process cannot be treated as running inside that preview. A Sites-hosted frontend can call an explicitly configured Hostinger Django API, or the Sites version can remain a presentation/contact preview while the complete Python-backed production application is deployed and tested on Hostinger. Never represent an unconnected preview form as persisted.
